Guide d’utilisation

Framework QA — quality gate pour projets web

Mode d’emploi pas à pas pour débutant · Windows · PowerShell

1. C’est quoi ?

Le framework QA est un outil en ligne de commande. Dans le dossier d’un projet (par exemple pilote-web), tu tapes qa test. L’outil lit un fichier de configuration, installe ce qui manque, lance les contrôles (lint, tests, sécurité, accessibilité, performance…), puis ouvre un rapport HTML dans le navigateur.

Tu n’as pas besoin de relancer chaque outil à la main. Une seule commande suffit.

2. Ce dont tu as besoin

  • Windows, avec PowerShell.
  • Node.js et npm (dans le terminal : node -v puis npm -v).
  • Le dossier qa_framework (le code de l’outil).
  • Le dossier du projet à tester (ex. pilote-web), avec un package.json.

À retenir : sur cet ordinateur, npm peut échouer à cause d’un certificat. Avant les commandes npm ou qa test, exécute :
$env:NODE_OPTIONS='--use-system-ca'

3. Préparer la commande qa (une seule fois)

Cette étape installe la commande qa sur ton PC. Tu ne la refais pas à chaque projet.

  1. Ouvre PowerShell.
  2. Va dans le dossier du framework :
cd "C:\Users\GrâceAdjetey\Documents\Mes projets\qa_framework"

3. Active le correctif certificat, puis installe et compile :

$env:NODE_OPTIONS='--use-system-ca'
npm install
npm run build
npm link

4. Vérifie que la commande existe :

qa --help

Tu dois voir Usage: qa et la commande test. Si qa n’est pas reconnu, ferme le terminal, rouvre-le, et réessaie. Après une modification du code du framework, refais seulement npm run build.

4. Lancer les tests sur un projet existant

Un projet existant (comme pilote-web) a déjà un package.json et un qa.config.json à la racine.

  1. Va dans le dossier du projet, pas dans qa_framework :
cd "C:\Users\GrâceAdjetey\Documents\Mes projets\pilote-web"

2. Active le correctif certificat (si tu viens d’ouvrir le terminal) :

$env:NODE_OPTIONS='--use-system-ca'

3. Lance la quality gate :

qa test

Pendant l’attente, un spinner (⠋ ⠙ ⠹ …) indique le contrôle en cours.

À la fin tu vois :

  • une ligne par contrôle : ✔ réussi, ✖ échec bloquant, ⚠ avertissement
  • PASS (tout va bien) ou FAIL (un contrôle obligatoire a échoué)
  • le rapport HTML qui s’ouvre dans le navigateur
  • un lien file://… dans le terminal (Ctrl + clic si besoin)

À retenir : le rapport est aussi ici : dossier-du-projet\.qa\report.html

5. Préparer un nouveau projet

Le framework ne crée pas un projet de zéro. Il a besoin d’un package.json et d’un qa.config.json. Ensuite, qa test installe beaucoup d’outils automatiquement.

5.1. Créer le projet

cd "C:\Users\GrâceAdjetey\Documents\Mes projets"
mkdir mon-projet
cd mon-projet
npm init -y

Si c’est une application web, crée-la avec ton outil habituel (Vite, etc.), puis place-toi à la racine de ce projet.

5.2. Créer qa.config.json

À la racine du projet, crée un fichier nommé exactement qa.config.json. Sans ce fichier : qa.config.json introuvable.

{
  "projectType": "web",
  "checks": {
    "lint": { "enabled": true, "required": true },
    "typecheck": { "enabled": true, "required": true },
    "unit": { "enabled": true, "required": true },
    "coverage": { "enabled": true, "required": true },
    "e2e": { "enabled": true, "required": true },
    "a11y": { "enabled": true, "required": false },
    "visual": { "enabled": true, "required": false },
    "audit": { "enabled": true, "required": true },
    "secrets": { "enabled": true, "required": true },
    "bundle": { "enabled": true, "required": false },
    "lighthouse": { "enabled": true, "required": false }
  }
}
  • enabled: true = le contrôle est lancé. false = il est ignoré.
  • required: true = un échec fait échouer toute la gate (FAIL). false = avertissement (⚠), la gate peut rester PASS.

À retenir : sur un projet tout neuf, commence petit : lint, typecheck et unit. Ajoute e2e, visual, lighthouse plus tard.

5.4. Ce que qa test installe tout seul

  • coverage : @vitest/coverage-v8
  • e2e : Playwright, playwright.config.ts, Chromium
  • a11y : @axe-core/playwright + script
  • visual : script test:visual (pas le fichier de test)
  • audit : script security:audit
  • secrets : secretlint + .secretlintrc.json
  • bundle : size-limit + .size-limit.json
  • lighthouse : paquets + perf-lighthouse.mjs
$env:NODE_OPTIONS='--use-system-ca'
qa test

6. Les fichiers de tests, c’est toi

  • Unitaires : fichiers *.test.ts (souvent dans src/).
  • Intégration : fichiers dans tests/.
  • E2E : e2e/*.spec.ts (Playwright).
  • Accessibilité : e2e/a11y/*.spec.ts
  • Visuel : e2e/visual/*.spec.ts. Au premier run local, Playwright crée le PNG de référence. Un vrai changement d’écran fera échouer le test jusqu’à npm run test:visual -- --update-snapshots si le changement est voulu.

7. Lire le résultat

  • ✔ = réussi
  • ✖ = échec d’un contrôle obligatoire → FAIL
  • ⚠ = échec d’un contrôle non obligatoire → la gate peut rester PASS

Fichiers produits :

projet\.qa\report.html
projet\.qa\report.json

8. Commandes utiles

qa --help
qa test
qa test --cwd "C:\chemin\vers\un-autre-projet"
qa test --fail-fast

9. Problèmes fréquents

qa n’est pas reconnu — refais npm run build puis npm link dans qa_framework. Ferme et rouvre PowerShell.

qa.config.json introuvable — tu n’es pas dans le bon dossier. cd vers le projet.

UNABLE_TO_VERIFY_LEAF_SIGNATURE — exécute $env:NODE_OPTIONS='--use-system-ca' puis relance.

Missing script: lint — ajoute le script dans package.json, ou désactive le check.

Le rapport ne s’ouvre pas — Ctrl + clic sur le lien file://, ou ouvre projet\.qa\report.html.

Tests visuels en échec après un changement d’écran — normal. Si c’est voulu : npm run test:visual -- --update-snapshots

10. Fiche mémo

Première installation de l’outil :

cd "...\qa_framework"
$env:NODE_OPTIONS='--use-system-ca'
npm install
npm run build
npm link

À chaque fois, sur un projet :

cd "...\mon-projet"
$env:NODE_OPTIONS='--use-system-ca'
qa test

À retenir : tu travailles toujours dans le dossier du projet à tester. qa_framework, c’est l’outil. pilote-web (ou mon-projet), c’est l’application contrôlée.
